Why it matters

The ruleset has no signature for this parameter shape, so the request is forwarded unchanged. The application answered identically to a direct upstream call, which proves the payload arrived — the 404 came from the app, not from the WAF.

Evidence · run #412, probe 17

GET /.wafscan/412-17?id=1%27%20OR%20%271%27%3D%271
Host: plex.example.com   X-Scan-Probe: 412-17

WAN      404  sha256 8f1c…a2  nginx/1.24.0
UPSTREAM 404  sha256 8f1c…a2  nginx/1.24.0
similarity 1.00 · no rule id in the request log

No credentials were sent, nothing was written, and the probe path does not exist in the application.

Fix

  • Patch the application to a release that parameterises this query (27.1.6).
  • Until then, add a WAF rule for UNION … SELECT in query strings and turn on the custom rule for booleans.

Compensating control

Turn on the access gate for this hostname: accounts + TOTP. It covers browser visitors, not API tokens, so the rule above still matters.
